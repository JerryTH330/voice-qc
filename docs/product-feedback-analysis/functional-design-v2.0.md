# 客户洞察功能设计 V2.3

## 0. 文档说明

- 文档版本：V2.3
- 产品范围：客户洞察 1.0
- 文档状态：已按确认口径修订，可进入业务、数据和技术联合评审
- 事实基线：`docs/项目现状与能力边界.md`
- 上一版本：客户洞察功能设计 V2.2
- 适用原则：现有能力作为基础，缺失能力通过 1.0 新增开发补齐，不因当前尚未实现而删减业务目标

### 0.1 本次修改摘要

1. 线上以第一条邀约类录音为 T0，线下以第一次真实到店事件为 T0。
2. 线上、线下统一支持 7 天、15 天、30 天观察窗口。
3. 结果分析只使用已经完整走完所选观察窗口的成熟客户批次；即使目标结果提前发生，也统一等待窗口结束后再进入结果分析，避免正负客群成熟度不一致。
4. 线上和线下均支持单客群洞察与 A/B 客群对比，A/B 不是强制前置条件。
5. 先按线索旅程判断客群，再在各客群内按手机号去重；同一手机号可因不同旅程分别进入不同客群。
6. 重叠客户可以分别保留在两个客群中，页面展示重叠数量，不默认排除。
7. 录音证据严格截断到结果发生前或观察窗口结束前。
8. 13 类标签默认在证据窗口内取并集；需要使用最后一次明确结果的标签必须另行确认。
9. 已有 7 项邀约 SOP 作为“已有 SOP 动作”直接进入销售动作洞察，复用现有完成、合格和证据结果，不重复开发识别；SOP 详情仍跳转专门页面。
10. 业务试驾事实与 AI 对话试驾状态分别保留、分别统计，不互相覆盖。
11. 阶段原因、SOP 未覆盖动作识别、竞品事实、AI 群体总结和候选标准动作明确为 1.0 新增开发。

## 1. 产品定位

客户洞察通过外部业务事实圈选客群，再聚合已有录音分析结果和 1.0 新增结构化结果，帮助管理人员理解不同阶段、不同结果客户在需求、难点、销售动作和竞品方面的差异。

核心链路为：

```text
外部业务事件和线索状态圈选客群
→ 聚合客群证据窗口内的可分析录音
→ 形成客户信号、阶段原因、销售动作和竞品事实
→ 支持单客群洞察或 A/B 对比
→ 下钻到客户、线索、录音、ASR 原文和业务事实
→ 生成可验证的管理摘要与标准动作候选
```

### 1.1 产品目标

1. 查看品牌、车型、组织在线上邀约和线下接待阶段的结果与录音覆盖。
2. 分析指定客群的客户需求、关注、抗性、阶段难点和竞品信息。
3. 比较不同结果客群的客户特征、阶段原因和销售动作差异。
4. 识别哪些销售动作与更好的阶段结果相关，并沉淀标准动作候选。
5. 让每个结论回到客户、线索旅程、录音、ASR 原文和外部业务事实。

### 1.2 非目标

1. 不替代其他产品建设完整的到店率、试驾率、成交率经营漏斗。
2. 不把录音覆盖客户等同于全部经营客户。
3. 不把客群差异或动作结果差异表达为严格因果。
4. 不向单个销售生成下一步跟进建议。
5. 1.0 不自动把标准动作候选写入正式 SOP 或质检规则。
6. 不新增报价、下订、交车、售后等独立录音采集场景。

## 2. 目标用户与使用场景

### 2.1 目标用户

- 厂端销售运营、产品、营销和市场情报人员
- 大区、经销商和门店管理人员
- 销售标准、培训和质检规则负责人

### 2.2 使用场景

- 单客群复盘：查看 7 日内已到店客户最集中的需求、难点、动作和竞品。
- 结果对比：比较 15 日内到店与 15 日未到店客户的差异。
- 线下复盘：比较到店后 30 日成交与到店后 30 日未成交客户的差异。
- 自定义状态对比：比较两个真实线索状态组合在同一观察窗口内的对话差异。
- 车型与组织复盘：定位问题集中车型、组织和销售动作。
- 案例复盘：从群体发现下钻到真实录音和业务事件。

### 3.3 1.0 不包含

- 自定义观察天数

- 模型训练、人工纠错和模型验收平台

## 4. 数据基础与核心对象

### 4.1 录音场景

| 阶段 | 来源 | 当前录音场景 |
|---|---|---|
| 线上邀约 | 云外呼 | 首触跟进、邀约到店、排程确认 |
| 线下接待 | 门店工牌 | 销售/门店接待、试乘试驾 |

系统不假设还存在报价、下订、交车或售后等独立录音。相关内容只有在以上五类录音中真实出现时才能被识别。

### 4.2 核心对象

#### 线索旅程

一条线索从第一条邀约类录音开始，到后续到店、试驾和线索状态变化形成的业务过程，是客群判断的基本单位。

#### 客户

在同一客群内部按手机号去重后的自然人，是群体统计单位。

#### 录音

最小内容分析事实。每条录音独立保存 ASR、13 类标签及其他分析结果。

#### 业务事件

来自外部系统的到店、试驾和线索状态事件。业务事件用于确定 T0、判断窗口内结果和提供业务上下文。

#### 证据窗口

从 T0 开始，到结果发生前或所选 N 日窗口结束前的可用录音范围。

### 4.3 可分析录音

内容洞察使用的录音必须：

1. 已进入系统；
2. 已完成 ASR；
3. 已产生相应分析结果；
4. 可以关联到当前线索旅程和阶段；
5. 发生在证据窗口内。

线上云外呼当前只对 30 秒及以上录音进行 ASR。30 秒以下录音单列为未进入内容分析，不进入客户信号、阶段原因、销售动作和竞品统计。

## 5. 客户、线索与去重规则

### 5.1 计算顺序

```text
线索旅程匹配业务事件
→ 判断线索旅程所属客群
→ 在每个客群内部按手机号去重
→ 聚合证据窗口内的可分析录音
```

### 5.2 具体规则

1. 先按线索旅程判断客群，不能先合并同手机号的全部线索。
2. 同一手机号在同一客群中只计算一次。
3. 同一手机号可以因不同线索旅程分别进入不同客群。
4. 同一手机号在 A、B 两组中都出现时，分别保留在对应客群统计中。
5. 页面展示 A、B 组重叠客户数和重叠率，但不默认把重叠客户从两组排除。
6. 重叠客户明细需要展示其不同线索旅程，避免用户误以为同一旅程被重复分组。

## 6. 观察窗口与客群判断

### 6.1 观察窗口

线上、线下统一支持：

- 7 天
- 15 天
- 30 天

N 表示用户当前选择的观察天数。自定义天数属于后续能力。

结果分析同时使用“完整样本批次”控制统计范围：

1. 每条旅程的观察期结束日为 `T0＋N 天`。
2. 页面“最近 1/7/15/30 日”指观察期结束日落在对应日期范围内的完整样本批次，不指最近刚进入阶段的客户。
3. 系统根据观察期结束日自动反推实际 T0 范围，并在页面直接展示。
4. 只有 `T0＋N 天` 不晚于当前数据截止时间的旅程才能进入结果分析。
5. 即使客户已在窗口内提前到店或成交，也等待观察期完整结束后，与未发生目标结果的客户在同一成熟度下统一进入分析。

### 6.2 线上邀约客群

线上 T0 为一条线索旅程中的第一条邀约类录音时间。

| 判断条件 | 客群名称 | 是否进入本次 N 日结果分析 |
|---|---|---|
| 已完整经过 N 天，且 T0 至 T0＋N 天内匹配到真实到店事件 | N 日内已到店 | 是 |
| 已完整经过 N 天，且 T0 至 T0＋N 天内未匹配到真实到店事件 | N 日未到店 | 是 |
| 尚未完整经过 N 天，无论是否已提前发生到店 | 未成熟批次 | 否 |

规则说明：

1. 到店只依据外部真实到店事件，不依据是否存在工牌录音，也不使用线索状态代替。
2. 客户在 T0＋N 天之后才到店，在当前 N 日口径下仍属于“N 日未到店”。
3. 切换更长观察窗口后，系统重新计算可选的完整样本批次和实际 T0 范围。
4. 未完整经过 N 天的客户不进入当前完整样本批次，也不形成第三种业务客群。

### 6.3 线下接待客群

线下 T0 为该线索旅程第一次真实到店事件时间。

用户先选择哪些真实线索状态属于本次“成交状态”，例如：

- 仅已下订
- 已下订＋异地成交
- 业务认可的其他状态组合

| 判断条件 | 客群名称 | 是否进入本次 N 日结果分析 |
|---|---|---|
| 已完整经过 N 天，且 T0 至 T0＋N 天内进入用户选择的成交状态 | 到店后 N 日成交 | 是 |
| 已完整经过 N 天，且 T0 至 T0＋N 天内未进入选定成交状态 | 到店后 N 日未成交 | 是 |
| 尚未完整经过 N 天，无论是否已提前进入成交状态 | 未成熟批次 | 否 |

数据前提：必须具备成交状态发生时间、下订时间或线索状态历史，才能准确判断“到店后 N 日内是否进入成交状态”。只有当前最新状态而没有发生时间时，不得计算历史 N 日结果。

### 6.4 自定义状态客群

除标准的“到店后 N 日成交/未成交”外，线下 A/B 模式允许用户选择其他真实线索状态组合。自定义状态组必须满足：

1. 状态事件发生在 T0 至 T0＋N 天内；
2. 使用相同的 N 日窗口；
3. 明确显示 A、B 组各自包含的状态；
4. 同一旅程命中多个状态时保留完整状态历史；
5. 同一旅程同时命中 A、B 状态组时可以进入两组，页面明确标记为重叠旅程，不默认排除；
6. 同一手机号因不同旅程进入两组时，按第 5 章规则分别保留。

## 7. 录音证据时间范围

| 阶段与客群 | 证据起点 | 证据终点 | 可使用录音 |
|---|---|---|---|
| N 日内已到店 | 第一条邀约类录音 | 首次到店事件发生前 | 首触跟进、邀约到店、排程确认 |
| N 日未到店 | 第一条邀约类录音 | T0＋N 天 | 首触跟进、邀约到店、排程确认 |
| 到店后 N 日成交 | 第一次真实到店事件 | 成交状态发生前 | 销售/门店接待、试乘试驾 |
| 到店后 N 日未成交 | 第一次真实到店事件 | T0＋N 天 | 销售/门店接待、试乘试驾 |
| 线下自定义状态客群 | 第一次真实到店事件 | 目标状态发生前或 T0＋N 天，以先发生者为准 | 销售/门店接待、试乘试驾 |

结果发生后或观察窗口结束后的录音不能用于解释窗口内结果。证据终点使用“发生前”，不把结果发生时点之后的对话纳入原因、动作或竞品分析。

## 8. 分析模式

线上和线下都支持单客群洞察与 A/B 客群对比。

### 8.1 模式差异

| 页面能力 | 单客群洞察 | A/B 客群对比 |
|---|---|---|
| 使用前提 | 选择一个客群 | 选择两个客群 |
| 适用问题 | 这个客群有什么特点 | 两个客群有什么差异 |
| 样本展示 | 一个客群的旅程数、客户数和录音数 | A、B 两组及重叠客户数 |
| 客户信号 | 客户数、占比、排行 | A/B 客户数、占比和百分点差值 |
| 阶段原因 | 高频原因和原因组合 | 原因差异和集中客群 |
| 销售动作 | 执行机会、完成率、SOP 合格率和案例 | 两组完成率、合格率、结果关联和差值 |
| 竞品 | 品牌、车型、配置和价格事实 | 两组提及率和事实差异 |
| AI 总结 | 单客群摘要和优先问题 | A/B 差异摘要和待验证假设 |
| 重叠客户 | 不适用 | 展示数量和明细，不默认排除 |

### 8.2 单客群示例

- 7 日内已到店
- 15 日未到店
- 到店后 7 日成交
- 到店后 30 日未成交
- 某个真实线索状态组合

### 8.3 A/B 示例

- 7 日内已到店 vs 7 日未到店
- 到店后 15 日成交 vs 到店后 15 日未成交
- 用户选择的状态组 A vs 状态组 B

A/B 对比不是所有分析的强制前置条件。用户可以先做单客群洞察，再切换到对比模式。

## 9. 13 类标签聚合

### 9.1 标签范围

当前聚合：抗性点、付款方式、决策阶段、意向车型、置换情况、购车时间、用车人、客户职业、对比竞品、试驾状态、购车场景、需求特征、预算区间。

### 9.2 默认聚合规则

1. 只使用客群证据窗口内的录音结果。
2. 同一手机号、同一标签值在同一客群中只计算一次。
3. 同一客户可以命中多个不同标签值。
4. 默认取证据窗口内命中标签值的并集。
5. 不直接复用“线索级 AI 意向取最后一条录音”的现行展示规则。
6. 如果某些状态型标签需要取“最后一次明确结果”，必须形成单独的业务规则清单并经确认后实施。

### 9.3 标签与新增阶段原因的关系

- 客户关注、需求和计划优先复用现有标签。
- 邀约难点、接待难点先使用抗性点、购车时间、决策阶段、预算、竞品等标签作为基础信号。
- 现有标签不能完整表达的阶段原因，通过 1.0 新增阶段原因识别补齐。
- AI 可以归纳原因组合，但每个原因必须回溯到录音证据。

## 10. 业务试驾事实与 AI 试驾标签

| 信息 | 来源 | 用途 |
|---|---|---|
| 业务试驾结果 | 外部试驾业务事件 | 判断客户是否真实完成试驾，保留试驾时间 |
| AI 对话试驾状态 | 录音分析：已试驾、未试驾、拒绝试驾、已约试驾 | 分析客户在对话中表达或被识别到的试驾状态 |

两种信息分别保留、分别统计：

1. 业务试驾事实不能覆盖 AI 对话试驾状态。
2. AI 对话试驾状态不能替代业务试驾事实。
3. 页面需要分别标注“业务事件”和“对话识别”。
4. 两者不合并成一个试驾指标；不一致时保留差异供数据和业务复盘。

## 11. 阶段原因识别（1.0 新增）

### 11.1 线上邀约难点

建议一级原因：

- 到店时间不便
- 距离或交通不便
- 购买紧迫性低
- 购车计划不明确
- 活动或权益吸引不足
- 价格或预算顾虑
- 产品顾虑
- 竞品比较未完成
- 家庭决策未完成
- 对销售或门店信任不足
- 明确拒绝继续沟通
- 其他

### 11.2 线下接待难点

建议一级原因：

- 产品能力不满足
- 具体配置不满足
- 价格或优惠不满意
- 金融成本或月供压力
- 置换估值不满意
- 权益、保险或赠品争议
- 竞品更有吸引力
- 家庭决策未完成
- 购车计划延后
- 品牌、售后或保值顾虑
- 交付周期不满足
- 其他

### 11.3 结构化字段

每条阶段原因至少保存：阶段、一级原因、二级原因、原因组合、客户/销售说话人、发生时间、录音 ID、ASR 证据、置信度和模型版本。

页面统一使用“高频难点”“客群差异”“关联信号”，不把识别结果直接命名为确定原因。

## 12. 统一销售动作层（已有 SOP＋新增识别）

### 12.1 设计原则

1. SOP 本质上是对已确定标准动作的执行检查。
2. 已被 SOP 覆盖的动作直接复用 SOP 结果，不再由新增动作模型重复识别。
3. 新增动作模型只识别 SOP 尚未覆盖的动作。
4. 已有 SOP 动作与新增识别动作使用统一动作编码、统一证据结构和统一客群统计口径。
5. 同一动作同时被 SOP 和新增模型识别时，以 SOP 映射结果为准，只统计一次。

### 12.2 已有线上邀约 SOP 动作

| 统一动作标签 | 现有 SOP 维度 | 数据来源 | 页面标识 |
|---|---|---|---|
| 确认意向车型 | 意向车型 | SOP 单项结果和实际话术证据 | 已有 SOP |
| 确认购车关注点 | 购车关注点 | SOP 单项结果和实际话术证据 | 已有 SOP |
| 确认对比车型 | 对比车型 | SOP 单项结果和实际话术证据 | 已有 SOP |
| 确认增换购情况 | 增换购情况 | SOP 单项结果和实际话术证据 | 已有 SOP |
| 确认计划购车时间 | 计划购车时间 | SOP 单项结果和实际话术证据 | 已有 SOP |
| 提出试乘试驾邀请 | 试乘试驾邀请 | SOP 单项结果和实际话术证据 | 已有 SOP |
| 提出添加微信邀请 | 添加微信邀请 | SOP 单项结果和实际话术证据 | 已有 SOP |

客户洞察直接展示以上动作的完成情况、合格情况、客群差异、结果关联和录音证据。完整 SOP 规则、全部核查详情和单录音质检仍在 SOP 专门页面查看。

### 12.3 完成与合格

- 动作完成：销售实际说出了对应核查或邀请内容。
- 动作合格：动作已完成，且关键信息满足现有 SOP 标准。

现有 SOP 数据接口需要为每个动作输出：

```text
action_code
action_name
completed
qualified
evidence
recording_id
```

整体结果同时保留 `required_items`、`completed_items`、`completion_percentage`、`qualified_items` 和 `qualified_percentage`。如果当前接口只有一个布尔值，需要先明确其代表“完成”还是“合格”，并补齐另一个字段；这属于接口标准化，不是重新开发 SOP 识别。

### 12.4 SOP 尚未覆盖的线上动作

新增模型只补充现有 7 项 SOP 未覆盖的动作，例如：

- 确认预算和付款方式
- 针对客户明确顾虑进行回应
- 结合客户需求进行产品价值解释
- 针对竞品进行差异化回应
- 约定下一次具体跟进动作

如果某个新增动作只是已有 SOP 动作的组成要素，例如试驾邀请中的时间安排或利益点说明，应作为已有 SOP 动作的合格要素，不再单独重复计为新动作。

### 12.5 线下销售动作

线下先盘点已有 SOP 规则：已有 SOP 覆盖的动作按相同方式直接复用；没有 SOP 覆盖的动作再新增识别。目标动作包括：

- 完整需求探询
- 结合需求进行产品讲解
- 安排并完成试乘试驾
- 针对客户场景演示配置
- 进行竞品对比
- 提供清晰报价并解释构成
- 提供金融测算或置换评估
- 处理关键异议
- 提出明确成交建议
- 约定后续动作

### 12.6 统一动作数据结构

每个动作记录：动作编码、动作名称、业务阶段、动作来源（已有 SOP/新增识别）、关联 SOP 规则 ID、客户触发信号、是否存在执行机会、是否完成、是否合格、发生时间、销售证据、客户回应证据、置信度和模型版本。

对于已有 SOP 动作：

- `completed` 和 `qualified` 直接使用 SOP 结果；
- SOP 已定义适用范围时直接复用；
- 如果 SOP 当前只给出命中/未命中而没有“执行机会”，需要补充适用场景或触发条件，避免使用全部录音作为错误分母。

对于新增识别动作：由新增模型判断执行机会、完成状态和证据。

## 13. 竞品事实（1.0 新增）

### 13.1 复用基础

现有“对比竞品”标签用于品牌级历史统计和模型校验。

### 13.2 新增字段

- 竞品品牌、车型、别名、年款和版本
- 配置项和配置比较关系
- 价格类型：裸车价、落地价、优惠、首付、月供等
- 金额和单位
- 地区和对话时间
- 客户自述、销售转述或其他来源
- 可信度和 ASR 证据

客户对话中提到的价格不等于官方价格。页面必须展示地区、时间、来源和可信度。

## 14. SOP 动作展示与其他质检结果边界

### 14.1 已有 SOP 在客户洞察中的展示

已有 SOP 规则映射为标准动作后，可以在客户洞察的“销售动作”模块中展示：

- 动作标签和“已有 SOP”标识；
- 完成客户数、完成率；
- 合格客户数、合格率；
- 单客群分布或 A/B 客群差异；
- 动作完成/合格与 N 日结果的关联；
- 实际销售话术证据。

这里复用现有 SOP 识别结果，不再调用新增动作模型对同一动作重复判断。

### 14.2 与现有 SOP 页面的分工

- 客户洞察回答：哪些标准动作在目标客群中执行得更多、合格得更多，与阶段结果有什么关联。
- SOP 页面回答：一条录音具体命中或未命中了哪些规则，规则标准和证据是什么。
- 客户洞察不复制完整 SOP 规则配置、单录音质检详情和未命中整改流程。

话术优势/缺陷仍只用于新增动作模型校验和正反案例候选；风险用于排除不适合作为优秀动作或候选标准的录音。

### 14.3 专门页面跳转

需要查看详情时，从客户洞察跳转到对应专门页面，并保留：

- 时间范围
- 组织、品牌和车型
- 业务阶段和录音场景
- 当前客群定义、N 日窗口和手机号集合或匿名客户集合

专门页面负责展示完整 SOP、话术和风险详情；客户洞察保留统一动作统计和必要提示。

## 15. AI 群体总结与标准动作候选（1.0 新增）

### 15.1 AI 群体总结

- 单客群模式：总结高频需求、难点、动作、竞品和优先复盘问题。
- A/B 模式：总结两组占比差异、关联信号、动作差异和待验证假设。
- 所有总结展示分析模式、客群定义、N 日窗口、客户数和证据引用。
- 筛选条件、观察窗口、客群或模式变化后，旧总结自动失效。

### 15.2 候选标准动作

已有 SOP 动作已经是正式标准，不再生成“标准动作候选”。候选只来源于 SOP 尚未覆盖、但在目标结果客群中更常出现且证据稳定的新增识别动作。

每个候选包含：

- 候选名称和适用阶段
- 客户触发信号
- 标准动作要求和完成标准
- 执行机会数、完成客户数和完成率；已有 SOP 动作同时展示合格率
- 执行与未执行客户的结果率和差值
- 成功证据和失败/反例证据
- 适用组织、车型和客群
- 样本量、稳定性和关联非因果提示

候选支持待验证、已采纳、不采纳三种状态，并记录编辑内容、处理原因、操作人和时间。候选被采纳后仍不自动写入 SOP；后续由现有 SOP 管理流程决定是否新增规则。

## 17. 全局筛选与页面模式

### 17.1 全局筛选

- 完整样本批次：最近 1/7/15/30 日或自定义
- 组织范围
- 品牌
- 车型
- 业务阶段
- 观察窗口：7/15/30 天
- 分析模式：单客群/A/B 对比

完整样本批次按观察期结束日 `T0＋N 天` 选择，系统自动反推并展示实际 T0 范围。自定义批次的结束日期不能晚于当前数据截止时间。页面不提供“最近刚进入阶段的客户＋N 日观察窗口”这种不完整组合。

### 17.2 阶段专属配置

#### 线上

- 单客群：选择“N 日内已到店”或“N 日未到店”。
- A/B：分别选择两个线上结果客群。

#### 线下

- 先选择本次成交状态组合。
- 单客群：选择“到店后 N 日成交”“到店后 N 日未成交”或自定义状态组。
- A/B：选择标准成交/未成交组合，或分别选择两个真实状态组。

切换模式时保留时间、组织、品牌、车型和 N 日窗口；不自动沿用与新模式不兼容的客群配置。

| N 日内到店客户占比 | 线上在 N 日内发生真实到店的客户比例 | N 日内已到店去重客户数 | 完整满足当前 N 日结果判断条件的线上去重客户数 |
| 到店后 N 日成交客户占比 | 线下在到店后 N 日内进入选定成交状态的客户比例 | 到店后 N 日成交去重客户数 | 完整满足当前 N 日结果判断条件的线下去重客户数 |
| 可分析客户覆盖率 | 结果客群中至少有一条可分析录音的客户比例 | 至少一条证据窗口内可分析录音的去重客户数 | 当前结果客群去重客户数 |
| ASR 分析覆盖率 | 满足 ASR 条件的录音中完成分析的比例 | 完成 ASR 并产生分析结果的录音数 | 当前范围内满足 ASR 条件的已接收录音数 |
| 标签客户占比 | 客群中命中某标签的客户比例 | 命中该标签的去重客户数 | 当前客群可分析去重客户数 |
| 阶段原因客户占比 | 客群中识别到某阶段原因的客户比例 | 命中该原因的去重客户数 | 当前客群可分析去重客户数 |
| A/B 占比差值 | 某标签、原因、动作或竞品在两组的占比差异 | A 组占比减 B 组占比 | 不适用，单位为百分点 |
| 特征关联结果率 | 具备某特征客户进入目标结果的比例 | 具备该特征且进入目标结果的去重客户数 | 具备该特征的去重客户数 |
| 动作执行机会数 | 某动作在当前客群中适用的客户数 | SOP 适用条件或新增模型识别到执行机会的去重客户数 | 不适用 |
| 动作完成率 | 适用客户中实际完成动作的比例 | 动作 `completed=true` 的去重客户数 | 识别到该动作执行机会的去重客户数 |
| SOP 动作合格率 | 已有 SOP 动作满足标准要求的客户比例 | SOP 动作 `qualified=true` 的去重客户数 | 该 SOP 动作适用的去重客户数 |
| 7 项 SOP 全完成录音占比 | 线上邀约 7 项全部完成的适用录音比例 | `completed_items=7` 的适用录音数 | 进入 7 项 SOP 检查的录音数 |
| 7 项 SOP 全合格录音占比 | 线上邀约 7 项全部合格的适用录音比例 | `qualified_items=7` 的适用录音数 | 进入 7 项 SOP 检查的录音数 |
| 动作关联结果率 | 执行动作客户进入目标结果的比例 | 执行动作且进入目标结果的去重客户数 | 执行该动作的去重客户数 |
| 竞品提及客户占比 | 客群中明确提及某竞品的客户比例 | 明确提及该竞品的去重客户数 | 当前客群可分析去重客户数 |
| 重叠客户数 | A、B 两组中都出现的手机号数量 | 同时出现在 A、B 两组的去重手机号数 | 不适用 |
| 重叠客户占比 | A、B 两组的客户重叠程度 | 同时出现在 A、B 两组的去重手机号数 | A、B 两组合并后的去重手机号数 |

补充规则：

1. 30 秒以下线上录音不进入 ASR 分析覆盖率分母，单列数量。
2. 同一客户、同一标签/原因/动作/竞品在同一客群中只计算一次。
3. A/B 对比同时展示占比、原始客户数和重叠客户数。
4. 动作关联结果率和特征关联结果率只表示关联。
5. 任一客群可分析客户少于 30 人时标记样本较少；单个主题少于 5 人时不生成强结论。
6. “完整满足 N 日结果判断条件”指客户已经完整经过 N 天；是否提前出现目标结果不改变成熟条件。
7. 同一统一动作编码同时存在 SOP 结果和新增模型结果时，只使用 SOP 结果，不能重复计数。
8. 客户级动作完成/合格统计在客群内按手机号去重；录音级 7 项全完成/全合格指标按适用录音统计，两种分母必须明确区分。

## 23. 术语与表达规范

### 23.1 统一术语

- 线上结果客群：N 日内已到店、N 日未到店
- 线下结果客群：到店后 N 日成交、到店后 N 日未成交
- 线上结果指标：N 日内到店客户占比
- 线下结果指标：到店后 N 日成交客户占比
- 完整样本批次：观察期结束日落在用户所选范围内、且已经完整经过 N 天的旅程
- 未成熟客户：尚未完整经过 N 天，不进入当前结果分析

### 23.2 允许表达

- 未到店客群高频难点
- 成交与未成交客群差异
- 录音中识别到的关联信号
- 在目标结果客群中更常执行
- 建议进一步复盘的问题或动作

### 23.3 禁止表达

- 某标签导致客户未到店
- 某动作一定提升成交率
- 没有工牌录音说明客户没有到店
- AI 试驾标签等于真实试驾结果
- 当前录音样本代表全部经营客户

## 24. 异常与排除处理

| 情况 | 处理方式 | 是否形成业务客群 |
|---|---|---|
| 尚未完整经过 N 天，无论是否已提前出现目标结果 | 不进入可选的完整样本批次，等待窗口结束 | 否 |
| 缺少状态发生时间或状态历史 | 不计算线下 N 日结果，列入数据排除 | 否 |
| 到店业务数据源不可用或关联失败 | 不计算线上结果，列入数据排除 | 否 |
| 没有可分析录音 | 可以保留业务结果统计，但不进入内容洞察 | 否，不新增客群 |
| 工牌录音未匹配 | 不进入线下内容洞察；不能解释为客户没有到店 | 否 |
| 缺手机号 | 保留录音级结果，不进入客户级统计 | 否 |
| 车型不明确 | 进入品牌或全部车型汇总，不进入具体车型对比 | 否 |
| 客户在 N 天后才出现结果 | 线上仍属于 N 日未到店；线下仍属于到店后 N 日未成交 | 是 |
| 同一手机号进入 A、B 两组 | 两组分别保留，展示重叠数量和明细 | 是 |

数据排除是数据质量处理，不是第三种业务客群。

## 25. 数据依赖与实施顺序

### 25.1 数据依赖

1. 录音：录音 ID、来源、场景、时间、时长、ASR 状态和文本。
2. 单录音分析：13 类标签、AI 意向及证据。
3. SOP 动作结果：规则 ID、7 项动作维度、单项 `completed`、单项 `qualified`、实际话术证据、整体完成率和整体合格率。
4. 其他后台校验数据：话术优势/缺陷、风险及证据。
5. 线索：线索 ID、手机号、品牌、车型、组织、顾问。
6. 到店：真实到店事件、到店时间、线索关联标识和组织。
7. 试驾：真实试驾事件、试驾时间和线索关联标识。
8. 状态历史：状态名称、状态发生时间、下订时间和异地成交信息。
9. 线索旅程：T0、观察窗口、结果事件、客群归属和数据排除原因。
10. 阶段原因：原因类型、证据、置信度和模型版本。
11. 统一销售动作：统一动作编码、动作来源、关联 SOP 规则、触发信号、执行机会、完成/合格状态、证据、置信度和模型版本。
12. 竞品事实：品牌、车型、版本、配置、价格、来源和可信度。
13. 标准动作候选：仅记录 SOP 未覆盖动作的候选内容、统计结果、证据、管理状态和操作日志。

### 25.2 实施顺序

#### P0：客群和证据基础

1. 建设线索旅程、T0 和 7/15/30 天窗口计算。
2. 接入到店、试驾和状态历史。
3. 实现单客群、A/B、手机号去重和重叠客户逻辑。
4. 实现结果前/窗口结束前的证据截断。

#### P1：聚合已有能力

1. 按证据窗口聚合 13 类标签。
2. 将线上 7 项 SOP 映射为统一动作标签，聚合完成、合格和证据结果。
3. 实现首页、线上、线下的样本、趋势、车型和组织分析。
4. 打通客户、线索、录音、ASR 和业务事实下钻。
5. 打通 SOP、话术和风险专门页面跳转。

#### P2：开发新增识别

1. 建设阶段原因标签和识别结果。
2. 盘点线下已有 SOP，并只对线上、线下 SOP 未覆盖动作新增执行机会和完成状态识别。
3. 建设竞品车型、版本、配置和价格事实。
4. 区分业务试驾事实与 AI 对话试驾状态。

#### P3：形成管理闭环

1. 实现 AI 单客群和 A/B 群体总结。
2. 实现优先关注问题和动作。
3. 仅从 SOP 未覆盖动作生成标准动作候选，并完成管理确认、操作记录和导出。
4. 完成小样本、数据排除和关联非因果限制验证。

## 26. 权限与安全

- 厂端查看授权范围内的汇总和组织下钻。
- 区域、经销商和门店只查看权限范围内的数据。
- 客户原声隐藏姓名、完整手机号和销售姓名。
- 重叠客户和导出文件同样遵循脱敏规则。
- 标准动作候选的编辑、采纳和否决需要管理权限并记录日志。
- 跳转 SOP、话术和风险专门页面时重新校验目标页面权限。

## 27. 1.0 验收标准

### 27.1 客群与窗口

- 线上 T0 为第一条邀约类录音，线下 T0 为第一次真实到店事件。
- 线上、线下均支持 7/15/30 天窗口。
- 页面按观察期结束日选择完整样本批次，并自动展示反推后的实际 T0 范围。
- 尚未完整经过 N 天的客户即使提前出现目标结果，也不进入当前结果分析。
- 线上正确生成“N 日内已到店”和“N 日未到店”。
- 线下根据用户选择的成交状态正确生成“到店后 N 日成交”和“到店后 N 日未成交”。
- 未成熟客户不进入结果分析，也不形成第三类客群。
- N 天后才出现结果的客户，线上仍归入 N 日未到店，线下仍归入到店后 N 日未成交。

### 27.2 模式与去重

- 线上、线下均支持单客群和 A/B 模式。
- 单客群模式不要求用户配置第二组。
- 先按线索旅程判断客群，再在客群内按手机号去重。
- 同一手机号可因不同旅程进入不同客群。
- 重叠客户在两组分别保留，并展示数量和旅程明细。

### 27.3 证据与标签

- 内容洞察只使用已完成 ASR 且在证据窗口内的录音。
- 结果发生后或窗口结束后的录音不进入解释证据。
- 13 类标签默认按窗口内并集聚合，同一客户同一标签值只计一次。
- 业务试驾事实与 AI 对话试驾状态分别展示、分别统计。
- 每个标签、原因、动作和竞品结论可以下钻到 ASR 原文。

### 27.4 新增能力

- 页面明确区分已有能力和 1.0 新增能力。
- 阶段原因、销售动作、竞品事实均有结构化结果和证据。
- 线上 7 项已有 SOP 动作显示“已有 SOP”标签，并直接复用 SOP 完成、合格和证据结果。
- 同一动作已有 SOP 结果时不再重复运行新增动作识别，也不重复计数。
- 已有 SOP 动作分别展示完成率和合格率；SOP 未覆盖动作基于新增动作事件和执行机会计算完成率。
- AI 支持单客群摘要和 A/B 差异摘要。
- 标准动作候选只来源于 SOP 未覆盖动作，并支持待验证、已采纳、不采纳及操作记录。

### 27.5 能力边界与表达

- 客户洞察可以在销售动作模块展示已有 SOP 动作及客群结果关联，但不复制完整 SOP 质检页面；话术优势/缺陷和风险不建设独立分析页面。
- 跳转专门页面时保留筛选、客群和 N 日窗口。
- 页面不出现第三种业务结果状态。
- 页面不把客群差异表述为确定原因或严格因果。
- 页面使用第 23 章统一术语。

## 28. 已确认默认规则与剩余业务决策

### 28.1 数据可行性结论

以下数据前提已经验证完整、可实现，不再作为待确认事项：

- 到店事件、试驾事件、状态发生时间和下订时间可用；
- 工牌录音匹配结果和手机号完整度满足建设要求；
- 数据保存周期支持 7/15/30 天窗口历史回算。

### 28.2 直接采用的 1.0 默认规则

以下事项不再要求业务逐项确认，1.0 直接采用统一默认规则：

| 原事项 | 1.0 默认规则 |
|---|---|
| 13 类标签如何聚合 | 全部采用证据窗口内标签并集，不设置“最后一次明确结果”的例外 |
| 线下可选状态和权限 | 直接读取业务系统真实状态字典；用户只看到并选择其数据权限范围内的状态，不预设唯一成交组合 |
| 阶段原因是否可扩展 | 一级原因使用第 11 章固定字典；AI 新发现的二级原因先进入“其他/待归类”，经后续运营整理后再进入正式统计 |
| 竞品可信度和价格异常 | 竞品字典由产品运营维护；模型阈值由模型验收确定；客户提及价格作为“对话事实”展示来源、时间和可信度，不自动当成官方价格，也不因价格异常直接删除 |
| 已有 SOP 动作如何处理 | 线上 7 项 SOP 直接作为已有标准动作；完成和合格使用现有 SOP 规则及证据，不再重复识别，也不生成候选标准 |
| 标准动作处理流程 | 统一使用待验证、已采纳、不采纳三种状态；1.0 默认支持表格导出，不自动写入 SOP 或质检规则 |

### 28.3 仅剩两项需要业务决定

#### 决策一：SOP 未覆盖动作怎样才算“完成”

已有 7 项 SOP 动作直接沿用现有完成和合格标准，不需要重新确认。这里只需要为 SOP 未覆盖的新动作确定最低完成标准。

示例：对于新增动作“约定下一次具体跟进”，需要决定：

- 只说“后续再联系”是否算完成；
- 还是必须说清下一次联系时间或具体跟进事项才算完成。

推荐规则：产品和模型团队按照第 12 章动作字典，为每个动作列出“触发条件、必须动作要素、完成示例、不完成示例”，由销售运营一次性确认后作为模型和验收标准。

#### 决策二：谁有权把标准动作候选标记为“已采纳”

需要业务指定系统中的确认角色。

推荐规则：

- 厂端销售运营管理员可以采纳或不采纳；
- 大区、经销商和门店可以查看、筛选和反馈，但不能改变厂端正式状态；
- 1.0 导出格式统一使用 Excel；
- 已采纳动作仍不自动写入 SOP 或质检规则。
