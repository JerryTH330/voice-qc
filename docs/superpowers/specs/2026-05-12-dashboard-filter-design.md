# 厂端看板 / 门店看板筛选条件改造设计

## 背景

厂端看板与门店看板当前都只有“业务场景”筛选，且交互以单选为主。此次需求需要在两页统一新增“数据来源”筛选，并将“业务场景”升级为受“数据来源”约束的多选筛选，以支持更细粒度的场景联动。

## 目标

1. 在厂端看板与门店看板统一新增“数据来源”筛选项，位置在“业务场景”前。
2. 将“业务场景”筛选项统一改为以下选项：
   - 全部
   - 首触跟进
   - 邀约进店
   - 排程确认
   - 进店接待
   - 试乘试驾
3. 实现“数据来源”与“业务场景”的联动：
   - 数据来源选择“全部”时，业务场景默认“全部”
   - 数据来源选择“云外呼”时，业务场景默认选中“首触跟进 / 邀约进店 / 排程确认”
   - 数据来源选择“工牌”时，业务场景默认选中“进店接待 / 试乘试驾”
4. 支持业务场景多选高亮，并允许用户在当前数据来源允许的范围内手动调整选中项。
5. 保持厂端与门店两页筛选行为一致，避免交互分叉。

## 非目标

1. 本次不重做筛选区整体样式，继续沿用现有 tab 风格。
2. 本次不重构整页所有图表与卡片的数据模型，只在现有 demo 数据基础上增加映射层兼容新筛选。
3. 本次不扩展到销售看板、录音列表或其他页面。

## 当前状态

### 门店看板

- 筛选 DOM 位于 `store-dashboard/index.html`
- 实际交互逻辑位于 `app-runtime.js`
- 当前“业务场景”只有：全部 / 邀约 / 门店接待 / 试乘试驾
- 当前状态模型依赖单值 `currentScene`

### 厂端看板

- 筛选 DOM 模板位于 `factory-dashboard/factory-dashboard.js`
- 交互逻辑同样在 `factory-dashboard/factory-dashboard.js`
- 当前“业务场景”同样以单选为主，并已有基于角色的联动逻辑

## 选型结论

采用方案 A：保留现有 tab UI，新增“数据来源”tab 组，并将“业务场景”从单值单选改为受数据来源约束的多选集合。

### 选择原因

1. 与现有视觉风格最一致，不会引入新的筛选控件形态。
2. DOM 结构与样式改动较小，主要修改集中在现有筛选区域。
3. 可以在不一次性重写全部图表逻辑的前提下，通过映射层兼容现有单值依赖。
4. 厂端与门店可以复用同一套筛选规则，降低后续维护成本。

## 交互设计

### 默认初始态

厂端看板与门店看板首次进入页面时均为：

- 数据来源：全部
- 业务场景：全部

### 数据来源选项

- 全部
- 云外呼
- 工牌

### 业务场景选项

- 全部
- 首触跟进
- 邀约进店
- 排程确认
- 进店接待
- 试乘试驾

### 数据来源与业务场景联动规则

#### 数据来源 = 全部

- 业务场景默认重置为“全部”
- 5 个具体业务场景全部可操作

#### 数据来源 = 云外呼

- 业务场景默认高亮：首触跟进 / 邀约进店 / 排程确认
- 可操作场景仅限：首触跟进 / 邀约进店 / 排程确认
- 进店接待 / 试乘试驾置灰不可点击

#### 数据来源 = 工牌

- 业务场景默认高亮：进店接待 / 试乘试驾
- 可操作场景仅限：进店接待 / 试乘试驾
- 首触跟进 / 邀约进店 / 排程确认置灰不可点击

### 业务场景点击规则

1. 点击“全部”时：
   - 清空其他具体场景
   - 仅“全部”高亮

2. 点击任意具体场景时：
   - 取消“全部”高亮
   - 切换该具体场景的选中状态

3. 当当前数据来源下所有允许的具体场景都被点满时：
   - 自动切回仅“全部”高亮

4. 禁用态场景：
   - 不可点击
   - 不参与“全部点满”的判断

## 状态模型设计

### 核心状态

两页统一引入以下筛选状态：

- `currentSource`：当前数据来源，取值为 `all / cloud / badge`
- `currentScenes`：当前业务场景集合，存储为数组或集合

建议统一以英文 key 表示内部状态，再映射到中文文案：

- `all`
- `first_follow`
- `invite_store`
- `schedule_confirm`
- `store_reception`
- `test_drive`

### 数据来源允许场景映射

- `all` → `first_follow / invite_store / schedule_confirm / store_reception / test_drive`
- `cloud` → `first_follow / invite_store / schedule_confirm`
- `badge` → `store_reception / test_drive`

### 数据来源默认场景映射

- `all` → `all`
- `cloud` → `first_follow + invite_store + schedule_confirm`
- `badge` → `store_reception + test_drive`

### 归一化输出

为了兼容现有依赖单值场景的逻辑，新增统一归一化方法：

1. 若当前为“全部”态，返回 `all`
2. 若只选中 1 个具体场景，返回该场景 key
3. 若选中多个具体场景但未覆盖全部允许项，返回组合 key 或场景集合描述对象

建议新增两层接口：

- `getCurrentSceneSelection()`：返回完整多选集合
- `getEffectiveSceneKey()`：返回供旧逻辑使用的归一化结果

这样可让旧模块先消费归一化结果，新模块再逐步过渡到直接消费场景集合。

## 结构改造设计

### 门店看板

#### DOM 改造

修改 `store-dashboard/index.html` 中的全局筛选栏：

1. 在“业务场景”前新增“数据来源”tab 组
2. 将“业务场景”tab 文案替换为 6 项新场景
3. 保留时间、车系筛选结构不变

#### 逻辑改造

修改 `app-runtime.js` 中门店看板筛选逻辑：

1. 替换现有 `currentScene` 单值状态为：
   - `currentSource`
   - `currentScenes`
2. 新增以下辅助方法：
   - 获取当前数据来源允许的场景集合
   - 获取当前数据来源默认场景集合
   - 判断当前是否处于“全部”态
   - 刷新业务场景按钮的 `active / disabled` 状态
   - 归一化当前场景选择结果
3. 调整全局筛选绑定逻辑：
   - “数据来源”点击时，重置业务场景到该来源的默认选中状态
   - “业务场景”点击时，按多选规则更新 `currentScenes`
4. 保留时间、车系筛选现有行为不变

### 厂端看板

#### DOM 改造

修改 `factory-dashboard/factory-dashboard.js` 中筛选栏模板：

1. 在“业务场景”前新增“数据来源”tab 组
2. 将“业务场景”tab 文案替换为 6 项新场景
3. 保持其余筛选布局不变

#### 逻辑改造

修改 `factory-dashboard/factory-dashboard.js` 中筛选绑定与场景联动逻辑：

1. 引入与门店侧一致的 `currentSource + currentScenes` 状态模型
2. 将现有场景 tab 单选绑定器升级为多选绑定器
3. 将已有的“角色 → 场景”联动思路调整为“数据来源 → 场景”联动
4. 对依赖旧单值场景的卡片、表格、图表逻辑统一通过归一化方法兼容

## 数据兼容设计

当前 demo 数据并未天然提供以下细分标签：

- 首触跟进
- 邀约进店
- 排程确认

因此本次采用映射层兼容，而不是同步重做全部数据结构。

### 映射策略

#### 云外呼类场景

以下 3 个新场景先映射到当前“邀约 / 电话邀约”数据桶：

- 首触跟进
- 邀约进店
- 排程确认

在 demo 展示口径下，厂端与门店看板中的“邀约录音数”及其直接相关的邀约链路指标需要同步拆分为上述 3 个子场景，而不是继续共用一组完全相同的邀约数据。也就是说，这 3 个场景虽然共享同一类原始数据来源，但前端展示层需要为它们提供彼此可区分的 demo 数值、趋势和摘要表现，避免用户切换场景后核心指标几乎不变化，造成筛选失真感。

拆分原则：

1. 首触跟进、邀约进店、排程确认三者都归属于“云外呼”数据来源。
2. 三者共享同一类邀约原始数据语义，但在 demo 映射层生成不同的展示结果。
3. 至少以下指标需要按 3 个云外呼子场景区分展示：
   - 邀约录音数
   - 与邀约录音数直接相关的 KPI 指标
   - 与邀约链路强相关的摘要文案、排行和趋势表现
4. 后续若接入真实细粒度标签，应由真实数据替换 demo 映射，不保留前端伪拆分逻辑。

#### 工牌类场景

以下 2 个新场景映射到现有线下场景：

- 进店接待 → 门店接待类数据
- 试乘试驾 → 试乘试驾类数据

### 兼容原则

1. 先保证筛选交互与页面状态联动正确。
2. 先保证各模块在新筛选下稳定渲染、不报错。
3. 后续若真实数据补齐更细粒度标签，只需替换映射表，不必重写 UI 与筛选交互框架。

## 模块生效范围

本次改造需要覆盖以下两类能力：

### 一、真实生效的能力

1. 数据来源筛选显示与切换
2. 业务场景多选高亮
3. 业务场景禁用态控制
4. 默认选中与“全部”排他规则
5. 厂端与门店两页统一行为
6. 厂端与门店看板中的邀约录音数，以及与邀约链路直接相关的核心展示指标，在 demo 口径下按“首触跟进 / 邀约进店 / 排程确认”拆分显示

### 二、通过归一化兼容生效的能力

1. KPI 卡片
2. 摘要文案
3. 排行榜列切换
4. 趋势图与明细卡片
5. 其他直接依赖旧场景单值判断的模块

## 异常与边界处理

1. 数据来源切换时，必须先清理旧来源下不合法的业务场景状态，再渲染新状态。
2. 禁用态场景即使之前被选中过，也必须在切换来源时取消。
3. 当业务场景处于“全部”态时，不应再同时保留任何具体场景 active。
4. 当业务场景为空集合时，应立即回退为“全部”，避免出现无筛选结果的非法状态。
5. 旧逻辑若无法识别组合场景 key，应统一走 `all` 或映射兼容分支，不能直接抛错。

## 测试设计

### 交互验证

1. 门店看板首屏默认：数据来源=全部，业务场景=全部
2. 厂端看板首屏默认：数据来源=全部，业务场景=全部
3. 切换到“云外呼”后：
   - 首触跟进 / 邀约进店 / 排程确认默认高亮
   - 进店接待 / 试乘试驾置灰
4. 切换到“工牌”后：
   - 进店接待 / 试乘试驾默认高亮
   - 首触跟进 / 邀约进店 / 排程确认置灰
5. 点击“全部”后：
   - 仅“全部”高亮
6. 点击具体场景后：
   - “全部”取消高亮
7. 点满当前允许范围内全部具体场景后：
   - 自动切回仅“全部”高亮

### 渲染验证

1. 两页筛选栏布局不换行错位
2. disabled 态按钮视觉明确
3. 切换不同来源和场景时，图表、榜单、摘要不报错
4. 现有时间筛选与车系筛选不受影响
5. 在“云外呼”下切换首触跟进 / 邀约进店 / 排程确认时，邀约录音数及相关邀约链路展示指标可见区分，不是三页完全相同

## 风险与控制

### 风险

1. 门店看板中存在较多直接依赖 `currentScene` 的分支判断，修改时容易遗漏。
2. 厂端看板已有旧的场景级联逻辑，替换过程中容易与新规则冲突。
3. 新增多选后，如果没有统一归一化接口，图表与文案模块会出现分叉实现。

### 控制措施

1. 两页统一使用相同的来源映射、默认场景映射与归一化方法。
2. 所有旧逻辑统一改为消费归一化接口，而不是直接读取原始按钮状态。
3. 先完成筛选状态与 UI 联动，再逐步接入下游卡片与图表渲染。

## 结论

本次改造以最小 UI 改动实现“数据来源 + 业务场景多选联动”，优先统一两页筛选行为，并通过映射层兼容现有 demo 数据与旧单值场景逻辑。这样可以在不扩大改造面的前提下，先完整交付用户可见交互，并为后续接入更细粒度真实数据保留稳定扩展点。
