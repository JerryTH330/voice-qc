# 优秀话术库月度沉淀设计（7 章节整理版）

## 第 1 部分：月度怎么跑、跑什么

### 1.1 运行节奏

优秀话术库采用月度离线沉淀，不做实时任务，也不做周度正式入库。

建议运行方式：

- 按月运行 1 次
- 在次月延迟启动，建议 `M+1 月第 7-10 天`

### 1.2 为什么不当月立刻结算

邀约到结果之间存在时间滞后。如果在月末立即结算，容易漏掉“当月邀约、次月初才到店/接待/试驾”的成功样本。

### 1.3 本月任务的输入范围

按业务类型拆两条样本池：

#### 邀约成功样本池

- 输入：邀约音频 ASR
- 判定条件：后链路满足成功到店 / 成功接待 / 成功试驾中的至少一个
- 目的：沉淀高到店邀约话术

#### 下定成功样本池

- 输入：接待音频 ASR + 试驾音频 ASR
- 判定条件：最终下定成功
- 目的：沉淀高成交接待 / 试驾话术

但当前 v1 只正式上线邀约，接待和试驾先保留空结构。

### 1.4 流程分层

整条流程分为 4 层：

1. 候选样本筛选层
2. 样本清洗层
3. 主题归纳层
4. 发布沉淀层

### 1.5 周度的定位

周度不适合作为正式入库周期，只适合作为未来可扩展的候选观察池；正式入库仍建议以月度为准。

### 1.6 这一部分的最终结论

- 主任务是月度
- 运行时间建议是次月延迟 7-10 天
- 入库单位是主题，不是单条音频
- 成功定义必须由业务结果反推，而不是由大模型自行判断

## 第 2 部分：后端 JSON 输出契约

### 2.1 schema 的用途

这里的 schema 不是提示词，也不是数据库表结构，而是“月度任务跑完后，后端最终要产出什么格式的数据”的定义。

它的用途是：

- 约束后端最终输出结果
- 作为前后端之间的数据合同
- 为后续前端展示、接口设计和落库设计提供统一结构

### 2.2 设计原则

后端不要直接输出一堆零散的展示文案，而要输出有层级的结构化结果。

推荐层级：

- 月包 `monthly_packages`
- 场景 `invite / reception / test_drive`
- 主题 `topics`
- 代表样本 `representative_samples`

### 2.3 低 token 成本版总体结构

后端最终维护两层结果：

1. **月包 monthly_packages**
   - 只包含当月新增成功邀约样本
   - 只对当月数据做 LLM 归纳
   - 产出：当月话术主题、代表样本、月份总结

2. **完整池 global_pool**
   - 不重跑全历史 ASR
   - 只把历次月包按规则合并
   - 产出：长期沉淀的优秀话术主题池

### 2.4 核心字段方向

#### 月包关注

- 月份
- 任务信息
- 邀约主题列表
- 每个主题的推荐话术
- 每个主题的代表样本
- 接待 / 试驾空结构

#### 完整池关注

- 长期主题
- 首次出现月份
- 最近验证月份
- 来源月份集合
- 最近 3 个月活跃程度
- 代表样本

### 2.5 这一部分的最终结论

- schema 是月度任务的输出合同
- 月包保存每个月独立产物
- 完整池保存长期沉淀主题
- 接待 / 试驾先保留同构空结构

## 第 3 部分：完整池如何合并

### 3.1 核心原则

月包永远独立保存，不回写、不覆盖。完整池只是聚合视图，不是重写历史结论。

### 3.2 什么情况下算同一个主题

建议同时满足以下 4 个条件才合并：

1. 同场景
2. 主标签一致
3. 动作路径一致
4. 训练目标一致

### 3.3 什么情况下必须拆开

即使标签接近，也不要强合并。以下情况必须拆开：

- 动作路径不同
- 适用客户阶段不同
- 培训落点不同

### 3.4 为了降低 token 成本建议补两个字段

每个主题除了主题名，再增加：

- `action_pattern`
- `training_goal`

这样完整池合并时主要靠规则，而不是反复让大模型重读全历史。

### 3.5 时间变化怎么处理

完整池需要保留：

- `first_seen_month`
- `last_seen_month`
- `source_months`
- `recent_3m_count`
- `status`

`status` 建议分为：

- `active`
- `observing`
- `stale`

### 3.6 前后冲突的处理方式

如果新主题和历史主题结论不完全一致：

- 不自动覆盖历史
- 保留两个主题
- 用活跃度和最近验证月份反映当前优先级
- 前端默认优先展示最近验证过的活跃主题

### 3.7 这一部分的最终结论

v1 先用规则合并：

`scene + primary_tags + action_pattern + training_goal`

## 第 4 部分：前端“优秀话术库”怎么改

### 4.1 页面默认视图

默认进入 **完整池**，而不是默认某个月。

推荐一级切换：

- 完整池
- 月度新增

### 4.2 顶部筛选区

建议改成：

1. 视图范围
2. 业务场景
3. 主题标签
4. 训练目标
5. 主题状态（完整池模式下）
6. 月份筛选（月度新增模式下）

### 4.3 统计卡

#### 完整池模式

- 长期沉淀主题数
- 最近 3 个月活跃主题数
- 累计代表样本数

#### 月度新增模式

- 本月新增主题数
- 本月入选代表样本数
- 本月高频主标签

### 4.4 左侧列表区

左侧展示“主题列表”，而不是单条话术条目。

每个主题卡片建议展示：

- 主题名
- 一句话总结
- 主标签
- 训练目标
- 状态
- 最近验证月份
- 代表样本数

### 4.5 右侧详情区

右侧详情建议拆成 4 块：

1. 主题总结
2. 推荐培训话术
3. 训练要点
4. 代表样本

### 4.6 接待 / 试驾的页面处理

接待和试驾应该保留在页面里，而且可以点击进入，但当前展示标准空态：

- 顶部结构保留
- 统计卡为 0
- 列表为空
- 详情区提示当前暂无数据

### 4.7 这一部分的最终结论

- 默认展示完整池
- 支持切换到月度新增
- 月份筛选只在月度新增模式下出现
- 接待 / 试驾保留入口，当前展示空态

## 第 5 部分：后端月度任务链路怎么跑

整条任务链建议分成 9 步，其中只有主题归纳用 LLM，其他尽量规则化。

### 5.1 输入层

读取：

- 邀约原始通话数据
- 现有邀约质检结果
- 业务结果数据
- 基础元数据

### 5.2 样本筛选

按月窗口筛出“邀约成功候选样本”：

- 场景是邀约
- 通话发生在当月
- 后链路满足成功到店 / 接待 / 试驾中的至少一个

### 5.3 质量过滤

剔除：

- `优势发掘` 为空
- 有高风险违规
- 通话太短或 ASR 太短
- 误触、售后、非真实购车对象
- 高度重复通话

### 5.4 优势明细展开

把每通话里的 `优势发掘[]` 拆成“优势原子项”，用于后续聚类。

### 5.5 去重与预归并

先用规则压缩相似项，减少大模型输入规模。

### 5.6 月度主题归纳

只在这一步使用 LLM，输出：

- 主题名
- 主题总结
- 动作路径
- 训练目标
- 推荐话术
- 训练要点
- 代表样本归属

### 5.7 代表样本选择

每个主题保留 3-5 条代表样本，优先：

1. A 级
2. 高置信度
3. 原文清晰
4. 样本不要完全重复

### 5.8 生成月包

把当月主题、代表样本和统计信息写入独立月包。

### 5.9 更新完整池

把月包按规则合并进完整池，不重跑全历史总结。

### 5.10 这一部分的最终结论

- 单条邀约分析复用现有打标
- 月度只归纳新增成功样本
- 全局只做规则合并
- 接待 / 试驾当前只保留空结构

## 第 6 部分：哪些字段必须落库，哪些只做任务产物

1. `monthly_topics`

### 6.5 建议作为任务产物保留的数据

以下更适合作为 JSON 或日志保存：

- 候选样本数

- 剔除原因分布
- 生成主题数
- 合并到完整池的数量
- 中间归并结果

以下数据建议只存引用：

- 原始 ASR 本体
- 已有邀约质检 JSON 本体

### 6.7 这一部分的最终结论

v1 正式保存主题和代表样本，运行日志和中间结果先做任务产物，不重复复制上游主数据。

## 第 7 部分：v1 最终收口

### 7.1 v1 要做的

#### 后端

1. 建立月度离线任务
2. 次月延迟 7-10 天启动
3. 只处理当月新增成功邀约样本
4. 复用现有邀约 `优势发掘[]`
5. 生成邀约月包
6. 维护邀约完整池
7. 预留接待 / 试驾空结构

#### 前端

1. 保留邀约 / 接待 / 试驾三个入口
2. 默认展示完整池
3. 支持切换到月度新增
4. 月度模式下支持月份筛选
5. 详情页展示代表样本和原句溯源
6. 接待 / 试驾显示标准空态

### 7.2 v1 明确不做的

1. 不做接待 / 试驾单条打标
2. 不做全历史 LLM 重算
3. 不做周度正式入库
4. 不做厂端单独视图页面
5. 不做太复杂的自动主题智能合并

### 7.3 v1 成功标准

如果上线后满足以下 4 条，则认为方案成立：

1. 每月能稳定产出邀约主题
2. 每个主题都能追到代表样本和原句
3. 前端既能看长期沉淀，也能看月度新增
4. token 成本可控，大模型只在月度主题归纳这一步使用

### 7.4 最终定义

这不是重做一套新的邀约质检系统，而是在现有邀约优劣势打标之上，加一层月度培训沉淀和长期话术池。

职责划分如下：

- 单条质检层：继续负责每条邀约通话的优劣势打标
- 月度训练层：从成功样本中筛选优秀动作并归纳培训主题
- 话术库展示层：把主题、推荐话术和代表样本组织成长期可复用的话术库
