# 优秀话术库月度归纳与交付包对齐设计

## 背景

当前优秀话术库相关工作已经产出三类资产：

1. 前端页面改造与 contract 驱动展示
2. 月度 / 长期池的示例 contract 数据
3. 月度归纳相关的中立 LLM 资产与 handoff 文档

但在继续推进时，范围需要进一步收紧：

- 单条邀约优劣势打标提示词不允许修改
- 月度层需要尽量从单条打标结果中“自然生长”出来
- mock 数据不能只是为了前端展示而编造，必须尽量贴近月度归纳脚本真实可能产出的字段和结构
- 当前除了 md/伪代码说明外，还需要一份更接近后端可落地编码的 Python 处理脚本骨架，便于后续同事改造成正式实现

因此需要重新定义本阶段真正的交付目标：

**不是单纯做一个页面 demo，而是把“单条打标 -> 月度归纳 -> 前端消费”的链路打通为一套可交给后端和前端同事的交付包。**

## 目标

1. 保持单条邀约打标提示词完全不变。
2. 只调整和完善月度主题归纳提示词与输出 schema。
3. 明确从单条打标结果到月度归纳输入的规则处理过程。
4. 新增一份 Python 处理脚本骨架，表达真实编码路径，而不只是伪代码。
5. 让 mock contract 数据与月度归纳脚本保持一致，尽量模拟真实月度产物。
6. 让前端页面消费的字段来源在逻辑上可追溯到：
   - 单条打标输出
   - 规则处理结果
   - 月度归纳 LLM 输出

## 非目标

1. 本次不修改单条邀约优劣势打标提示词。
2. 本次不新增接待、试驾单条打标体系。
3. 本次不接入真实后端 API。
4. 本次不直接实现正式调度、数据库写入、生产级模型调用 SDK。
5. 本次不把接待、试驾扩成完整真实主题，只保留结构和空态能力。

## 已确定约束

### 单条层约束

当前可用的单条邀约打标结果已经固定，主要可消费字段来自：

- `优势发掘[]`
- `高风险违规点[]`
- `对话统计`
- 关联时间与原文

本次后续所有设计都必须建立在这个前提之上：

**月度层只能复用和加工单条输出，不能反推要求单条提示词额外新增字段。**

### 页面层约束

前端页面当前已经具备：

- 完整池 / 月度新增的双模式
- 邀约 / 接待 / 试驾的场景入口
- contract 驱动的主题列表和详情结构

但页面效果仍不完全符合预期，例如：

- “训练目标”表达不够直观
- 详情区位置和阅读动线不理想
- 页面观感受 mock 数据密度影响较大

这些属于下一轮 UI 调整内容，本轮先优先保证数据和月度产物逻辑对齐。

### 交付对象约束

本轮产出需要分别便于：

- 后端同事理解如何把单条打标结果转成月度输入，再组织成月度产物
- 前端同事理解当前页面消费的字段来自哪里，以及后续接真实 API 时需要保持哪些 contract 字段不变

## 链路重定义

本轮采用以下明确链路：

1. 单条邀约打标结果（不改）
2. 规则处理层
3. 月度归纳 LLM 输入
4. 月度归纳 LLM 输出
5. `monthly_packages`
6. `global_pool`
7. 前端页面消费

### 1. 单条邀约打标结果

上游已有结果，作为唯一可信的“单条证据层”。

### 2. 规则处理层

这层不依赖 LLM，职责是：

- 过滤出成功邀约样本
- 剔除不应进入优秀话术库的样本
- 展开 `优势发掘[]`
- 形成月度归纳所需的归一化输入

### 3. 月度归纳 LLM 输入

月度归纳模型不再直接吃整段 ASR，而是优先吃结构化输入：

- `call_id`
- `success_result`
- `tag_code`
- `tag_name`
- `confidence`
- `level`
- `quote`
- `replicable_point`
- 必要时补充 `source_month`、`scene`

### 4. 月度归纳 LLM 输出

月度层输出的职责是：

- 按主题归纳
- 生成推荐话术
- 输出训练要点
- 保留代表样本
- 补出前端真正需要、但单条层不会直接给出的主题级字段

### 5. monthly_packages

月度归纳 LLM 输出经校验后落入月包，作为“月度新增模式”的直接数据源。

### 6. global_pool

由规则处理层基于月包合并得到，不需要每次全历史重跑 LLM。

### 7. 前端页面消费

前端仍然只消费 contract，不应该知道月度生成时的具体内部过程。

## 本轮交付物

本轮最终要形成 3 个核心交付物。

### A. 月度归纳提示词与输出 schema

该提示词只面向“月度主题归纳”这一步，不能替代单条打标提示词。

它需要明确：

1. 输入来自单条打标结果的哪些字段
2. 不要重新判断单条优劣势
3. 如何按主题归纳
4. 如何挑选代表样本
5. 输出需要满足哪些主题级字段
6. 输出 schema 必须可直接转入 `monthly_packages`

### B. Python 处理脚本骨架

该脚本是给后端同事的编码参考骨架，不是生产版实现。

它需要表达的真实处理职责包括：

1. 读取单条打标结果
2. 过滤成功邀约样本
3. 展开 `优势发掘[]`
4. 构造月度归纳 LLM 输入
5. 调用月度归纳提示词
6. 校验 LLM 输出
7. 写入 `monthly_packages`
8. 合并得到 `global_pool`

### C. 扩充后的 mock contract 数据

这批 mock 数据不再只是“前端假展示数据”，而应该尽量模拟 Python 处理脚本 + 月度归纳 LLM 真正可能生成出的结果。

## 月度归纳提示词的职责边界

### 提示词必须做的

- 把多个成功样本中的优势动作聚成主题
- 为每个主题生成：
  - `topic_id`
  - `topic_name`
  - `primary_tags`
  - `action_pattern`
  - `training_goal`
  - `summary`
  - `recommended_script`
  - `training_points`
  - `representative_samples`

### 提示词不能做的

- 不能重新判断单条是否构成优势
- 不能推翻上游单条标签
- 不能自由发明与上游无关的单条证据
- 不能直接假设接待 / 试驾当前已有同样完备的单条层输入

### 提示词与前端字段的关系

前端详情区真正依赖、但单条层未必天然具备的字段，如：

- 主题摘要
- 推荐话术
- 训练要点
- 适用场景
- 避免场景

都应该由月度归纳输出补齐，而不是要求单条层去提供。

## Python 处理脚本骨架设计

### 脚本定位

Python 脚本不是最终后端服务，但要足够接近真实实现，让后端同事能低成本改造成正式代码。

### 模块职责建议

建议脚本至少拆成以下逻辑单元：

1. `load_single_call_results`
   - 读取单条邀约打标结果

2. `filter_success_invites`
   - 根据业务结果筛出成功邀约样本

3. `expand_advantages`
   - 把每条通话里的 `优势发掘[]` 展开为月度归纳原子项

4. `build_monthly_llm_input`
   - 组装月度归纳输入 JSON

5. `build_monthly_prompt`
   - 生成提示词文本

6. `validate_monthly_output`
   - 校验 LLM 输出结构

7. `build_monthly_package`
   - 生成标准 `monthly_packages` 数据

8. `merge_global_pool`
   - 从多个月包按规则合并长期主题池

### 为什么要出 Python

因为当前只有 md/伪代码，对后端同事来说不够“可改造”。

Python 骨架的价值在于：

- 更容易映射到真实后端实现
- 更利于看清字段流转路径
- 能暴露哪些字段是规则层产出，哪些字段是 LLM 层产出

## mock 数据扩充原则

### 原则 1：从单条层可推导

每个 mock 主题下的代表样本必须尽量能对照到单条输出会给的字段：

- 标签
- 置信度
- 等级
- 引用原句
- 可复制点
- 时间片段
- 成功结果

### 原则 2：主题字段来自月度层

主题名、推荐话术、训练要点等内容，应看起来像“月度归纳 LLM 输出”，而不是人工随意补文案。

### 原则 3：同月与长期池逻辑一致

- 月包中的主题是当月视角
- 完整池中的主题是跨月聚合视角
- 两者字段命名保持一致
- 长期池新增时间性字段：
  - `first_seen_month`
  - `last_seen_month`
  - `source_months`
  - `recent_3m_count`
  - `status`

### 原则 4：先只扩邀约

本轮 mock 只深扩邀约：

- `2026-05` 月包扩成 5 个主题
- `2026-04` 月包扩成 4 个主题
- `global_pool.invite` 扩成 7 个主题

接待 / 试驾继续保留结构和空态，不假装已经具备真实沉淀能力。

## 与单条打标提示词的对照关系

由于单条打标提示词不能改，本轮需要明确：

### 可直接复用的字段

- `标签编码`
- `问题类型 / 亮点类型`
- `判定置信度`
- `亮点级别`
- `具体描述`
- `可复制点`
- `开始时间`
- `结束时间`
- `关联原文`
- `对话统计`

### 不能直接从单条层拿到、需要月度层补的字段

- 主题名
- 主题摘要
- 主题动作路径
- 训练目标
- 推荐话术
- 训练要点
- 适用场景
- 避免场景
- 长期池状态字段

这意味着：

**如果前端缺的是主题级字段，不应反推改单条提示词，而应在月度归纳 prompt 或 Python 处理层补出来。**

## 当前页面与数据的配合方式

本轮优先保证数据和脚本逻辑对齐，页面观感问题第二轮再处理。

已经明确的页面偏好包括：

1. 进入“月度新增”后才显示月份切换器
2. “训练目标”文案后续需要更换为更直观的表达
3. 详情区当前呈现方式不够符合预期，后续单独调

因此本轮不以页面视觉优化为目标，而以“数据链路可交接、可解释、可编码”为目标。

## 最终建议

下一阶段真正的实现顺序应该是：

1. 先补月度归纳提示词
2. 再补 Python 处理脚本骨架
3. 再让 mock contract 数据按这套链路扩充
4. 最后再做第二轮页面表现优化

这样可以确保：

- 后端同事拿到的不只是文档，而是可直接改造的骨架
- 前端同事拿到的不只是静态 mock，而是对真实后端输出有约束力的 contract
- 页面后续改动不会继续脱离真实数据来源
