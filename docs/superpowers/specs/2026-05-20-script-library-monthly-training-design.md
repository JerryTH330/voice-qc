# 优秀话术库月度沉淀设计

## 背景

当前“优秀话术库”页面已经具备筛选区、统计卡、列表区和详情区的页面骨架，但内容仍是静态展示，尚未接入真实沉淀流程。页面模板位于 [script-library/index.html](../../script-library/index.html)。

本次需求希望从邀约、接待、试驾录音的 ASR 文本中筛出成功样本，沉淀成可培训、可复用、可回溯的优秀话术库内容。

现阶段已有一个稳定运行的邀约单条质检流程：

- 每条邀约通话会输出固定标签体系 `T01-T10`
- 每条通话会给出 `优势发掘`、`待改善短板`、`高风险违规点`、时间定位和关联原文
- 该流程强调证据约束、固定标签和可回溯性

因此本次设计不应重新发明一套邀约单条分析，而应在现有邀约质检结果之上增加“月度培训沉淀”能力。

## 目标

1. 建立一条按月运行的离线沉淀流程，从成功邀约样本中生成培训导向的话术主题。
2. 复用现有邀约单条质检结果，避免对邀约成功 ASR 进行重复的大模型单条优劣势分析。
3. 生成两层结果：
   - 月包：保留每个月独立的话术主题和代表样本
   - 完整池：跨月沉淀长期有效的优秀话术主题
4. 前端默认展示完整池，同时支持切换查看某个月的月度新增内容。
5. 为接待、试驾场景预留同构结构和页面入口，当前允许数据为空但不隐藏入口。
6. 保留主题级培训内容和代表样本证据链，支持回溯到单条通话原文片段。

## 非目标

1. 本次不重跑邀约单条质检，不替代现有邀约优劣势打标流程。
2. 本次不为接待、试驾新增单条打标体系，两个场景先保留空结构。
3. 本次不按周正式入库，周度最多作为后续可扩展的候选观察池。
4. 本次不做全历史成功邀约 ASR 的月度全量重算。
5. 本次不单独设计厂端视角页面，只在培训导向中兼顾“可落地执行”。
6. 本次不改造整个页面骨架，只在现有话术库结构上调整信息语义与数据来源。

## 现状与约束

### 页面现状

当前“优秀话术库”页面模板位于 [script-library/index.html:121-186](../../script-library/index.html#L121-L186)，已经具备以下结构：

- 顶部筛选卡片
- 三张统计卡
- 左侧列表区
- 右侧详情区

这套结构适合继续沿用，不需要推翻重做。

### 数据现状

1. 现有单条质检能力仅覆盖邀约场景。
2. 邀约单条质检结果已经具备固定标签、时间定位、关联原文、可复制点等结构化字段。
3. 接待、试驾暂无对应的单条打标体系。
4. 成功结果来自业务链路，不应由大模型自行推断。

### 成本约束

1. 每月不适合把全历史 ASR 原文重新喂给大模型。
2. 需要尽量用现有结构化结果和规则合并降低 token 成本。
3. 允许只对“当月新增成功邀约样本”做主题归纳。

## 方案结论

采用“月包 + 完整池”的双层沉淀方案。

### 总体思路

1. **月包**
   - 每个月独立生成一次
   - 只处理当月新增的成功邀约样本
   - 只对当月候选样本做主题归纳
   - 保留当月主题、代表样本、培训总结

2. **完整池**
   - 不重跑全历史 ASR
   - 不重跑全历史大模型总结
   - 只把历次月包按规则合并为长期沉淀主题
   - 用时间字段和状态字段表达“是否仍然活跃”

### 为什么不只做月度视图

如果页面只按月份分开展示，会有以下问题：

- 用户不方便快速查看长期沉淀下来的优秀话术
- 相同主题可能在不同月份重复出现，难以形成长期培训目录
- 只能看“当月产物”，不利于积累稳定的方法论

### 为什么不只做一个历史大池

如果只做一个全量历史池，也会有以下问题：

- 旧话术可能长期占位，掩盖最近更有效的表达方式
- 不容易回看某个月到底新增了什么内容
- 无法保证历史结论不被后续汇总过程覆盖

### 最终结论

- 底层数据按月独立保存
- 上层产品默认展示完整池
- 需要时再切换到月度新增模式查看某个月的独立结果

## 运行节奏与观察窗口

### 运行节奏

优秀话术库沉淀任务采用月度离线运行，而不是实时任务或周度正式任务。

建议运行时间：

- 每月运行 1 次
- 在次月延迟执行，建议 `M+1 月第 7-10 天`

### 选择原因

对于邀约场景，客户的后续动作存在时间滞后。如果在当月最后一天立即结算，会漏掉“当月邀约、次月初才完成到店/接待/试驾”的样本。

### 观察窗口

以 2026-05 月包为例：

- `invite_observe_start = 2026-05-01`
- `invite_observe_end = 2026-05-31`
- `conversion_cutoff = 2026-06-08`

## 场景策略

### 邀约

邀约是 v1 唯一正式上线的数据场景。

策略如下：

1. 复用现有邀约单条质检输出
2. 不重新对单条成功邀约 ASR 做优劣势分析
3. 月度只做成功样本筛选、优势提取、主题归纳、代表样本选择

### 接待

接待场景保留结构和页面入口，但当前不生成主题，数据返回空数组。

### 试驾

试驾场景保留结构和页面入口，但当前不生成主题，数据返回空数组。

### 页面处理原则

- 邀约 / 接待 / 试驾三个入口始终存在
- 接待 / 试驾允许进入页面
- 当前为空态，不使用不可点击或直接隐藏的处理方式

## 输入数据与样本筛选

### 输入数据

月度任务读取以下 4 类输入：

1. **邀约原始通话数据**
   - `call_id`
   - `audio_id`
   - `store_id`
   - `sales_id`
   - `call_time`
   - `raw_asr`

2. **现有邀约质检结果**
   - 单条 JSON 结果
   - 重点复用 `优势发掘[]`、`高风险违规点[]`、`对话统计`

3. **业务结果数据**
   - 是否成功到店
   - 是否成功接待
   - 是否成功试驾

4. **基础元数据**
   - 门店、销售、车型、线索来源等
   - v1 没有这些字段也可运行，但保留扩展口

### 成功样本定义

邀约成功样本不是由大模型主观判断，而是由业务结果反推得到。

候选池定义：

- 通话场景 = 邀约
- 通话发生时间落在当月观察窗口内
- 后链路满足以下条件之一：
  - 成功到店
  - 成功接待
  - 成功试驾

### 质量过滤

候选池需要继续剔除不适合进入优秀话术库的样本：

- `优势发掘` 为空
- 存在明确高风险违规点
- 通话过短或 ASR 过短
- 明显误触、非真实购车对象、售后咨询
- 同一客户/同一销售高度重复通话，只保留更优一条

## 输出契约定位

本设计中的 schema 指的是“月度任务跑完后，后端最终要交给前端的一份统一结构化结果”。

它不是：

- 提示词
- 数据库表结构
- 页面文案稿
- 给业务直接阅读的操作手册

它是：

- 月度话术库任务的输出格式
- 前后端之间的数据合同
- 也是后续落库与接口设计的基础对象模型

## 邀约场景的复用策略

### 复用原则

邀约场景不需要再对全量成功 ASR 原文做一遍新的单条优劣势分析。

原因如下：

1. 现有邀约单条质检已经给出了固定标签、时间定位、原文证据和可复制点。
2. 月度沉淀真正缺少的是“跨样本的主题归纳”，而不是“再判断一次单条亮点”。
3. 重新分析全量 ASR 会产生明显 token 浪费。

### 正确分层

邀约场景应拆成 3 层：

1. **单条层**
   - 直接复用现有邀约质检结果
   - 重点使用 `优势发掘[]`

2. **月度归纳层**
   - 对当月成功样本的结构化优势项做主题归纳
   - 生成适合培训的主题和推荐话术

3. **原文回溯层**
   - 需要时使用原始 ASR 提取代表原句、校验训练引用
   - 不作为每月再次大规模单条分析的主输入

## 月度任务链路

整条月度任务建议分为 9 步，其中只有月度主题归纳一步使用大模型。

### 1. 输入层

读取邀约原始通话、邀约单条质检、业务结果和基础元数据。

### 2. 成功样本筛选

在月观察窗口内筛出邀约成功候选池。

### 3. 质量过滤

剔除无优势、高风险、误触、无效短通话和高度重复样本。

### 4. 优势明细展开

把每条通话中的 `优势发掘[]` 拆成优势原子项，形成统一中间结构。

### 5. 去重与预归并

先按规则压缩相似优势项，减少大模型输入规模。

### 6. 月度主题归纳

让大模型基于“优势原子项集合”输出：

- 主题名
- 总结
- 动作路径
- 训练目标
- 推荐话术
- 训练要点
- 代表样本归属

### 7. 代表样本选择

每个主题下保留 3-5 条代表样本，优先 A 级、高置信度、原文清晰的样本。

### 8. 生成月包

把当月结果写成独立月包。

### 9. 更新完整池

把本月月包按规则合并进完整池，不重跑全历史大模型总结。

## 完整池合并规则

### 合并原则

月包永远独立保存，不回写、不覆盖。完整池只是聚合视图，不是改写历史。

### 同主题合并条件

建议同时满足以下 4 个条件才合并为同一个长期主题：

1. **同场景**
   - 当前 v1 固定为邀约

2. **主标签一致**
   - 例如都以 `T09 到店邀约推进` 为主
   - 或都以 `T01 深度需求挖掘 + T09 到店邀约推进` 为主组合

3. **动作路径一致**
   - 例如都是“需求挖掘 -> 到店推进”
   - 或都是“资料承接 -> 微信留资”

4. **训练目标一致**
   - 例如都是为了提升到店确认率

### 必须拆开的情况

即使标签接近，也不要强合并。以下情况必须拆开：

- 动作路径不同
- 适用客户阶段不同
- 培训落点不同

### v1 合并键建议

v1 先使用以下组合键做低成本规则合并：

- `scene + primary_tags + action_pattern + training_goal`

## 时间变化与主题状态

完整池必须能表达“哪些主题仍然活跃、哪些主题只是历史沉淀”。

### 建议保留字段

- `first_seen_month`
- `last_seen_month`
- `source_months`
- `recent_3m_count`
- `status`

### 状态定义

- `active`：最近 3 个月持续出现
- `observing`：新出现，尚未验证是否会稳定沉淀
- `stale`：历史出现过，但最近长时间未再验证

### 冲突处理原则

如果某个月新主题和历史主题的结论存在差异：

- 不自动覆盖历史主题
- 同时保留两者
- 通过 `last_seen_month`、`recent_3m_count` 和 `status` 反映当前活跃程度
- 前端默认优先展示最近验证过且状态为 `active` 的主题

## 前端展示设计

### 页面主模式

话术库页面默认进入“完整池”模式，而不是默认进入某个月份。

推荐一级切换：

- `完整池`
- `月度新增`

### 业务场景入口

页面中始终保留：

- 邀约
- 接待
- 试驾

其中：

- 邀约当前有真实数据
- 接待、试驾当前允许进入，但显示标准空态

### 顶部筛选区

现有筛选区建议改为：

1. **视图范围**
   - 完整池
   - 月度新增

2. **业务场景**
   - 邀约
   - 接待
   - 试驾

3. **主题标签**
   - `T01-T10`

4. **训练目标**
   - 提升到店确认率
   - 提升微信承接率
   - 降低客户流失
   - 提高需求探询质量

5. **主题状态**
   - 仅在完整池模式下显示
   - `active / observing / stale`

6. **月份筛选**
   - 仅在月度新增模式下显示

### 统计卡

#### 完整池模式

显示：

- 长期沉淀主题数
- 最近 3 个月活跃主题数
- 累计代表样本数

#### 月度新增模式

显示：

- 本月新增主题数
- 本月入选代表样本数
- 本月高频主标签

### 左侧列表区

左侧列表展示“主题卡片”，而不是单条话术条目。

每个主题卡片建议展示：

- 主题名
- 一句话总结
- 主标签
- 训练目标
- 状态
- 最近验证月份
- 代表样本数

### 右侧详情区

右侧详情建议拆成 4 块：

1. **主题总结**
   - 主题结论
   - 为什么有效
   - 适用场景
   - 不适用边界

2. **推荐培训话术**
   - 推荐表达
   - 动作顺序
   - 培训提示

3. **训练要点**
   - 要先问什么
   - 什么时候推进到店
   - 什么时候接微信
   - 哪些边界不能乱承诺

4. **代表样本**
   - 通话/音频 ID
   - 门店/销售
   - 来源月份
   - 命中的优势标签
   - 关键原句
   - 时间片段
   - 可复制点

### 空态设计

接待、试驾场景需要保留统一布局，但展示空态：

- 顶部筛选区仍显示
- 统计卡显示 `0`
- 列表区为空
- 详情区提示：当前暂无数据，后续接入单条打标与月度沉淀后展示
- 可补充一句：当前仅邀约场景已上线

### 二、建议保留为任务产物的数据

以下信息对排查任务质量很有用，但不一定需要设计成正式业务表：

- 总候选样本数
- 过滤后样本数
- 剔除原因分布
- 生成主题数

v1 可以先把它们保存为任务 JSON 或运行日志。

### 三、不建议重复保存的数据

以下数据已经在上游系统中存在，本模块适合保存引用，不适合重复复制主数据：

- 原始 ASR 本体
- 现有邀约单条质检结果本体

## v1 范围收口

### v1 要做的

#### 后端

1. 建立按月运行的离线任务
2. 次月延迟 7-10 天启动
3. 只处理当月新增成功邀约样本
4. 复用现有邀约 `优势发掘[]`
5. 生成邀约月包
6. 维护邀约完整池
7. 为接待、试驾保留空结构

#### 前端

1. 保留邀约 / 接待 / 试驾三个场景入口
2. 默认展示完整池
3. 支持切换到月度新增模式
4. 月度新增模式支持月份筛选
5. 详情页必须展示代表样本和原句溯源
6. 接待、试驾当前显示标准空态

### v1 明确不做的

1. 不做接待、试驾单条打标
2. 不做全历史大模型重算
3. 不做周度正式入库
4. 不做厂端单独视图页面
5. 不做过于复杂的自动主题智能合并

## 成功标准

如果 v1 上线后满足以下条件，则认为方案成立：

1. 每月能稳定产出邀约主题
2. 每个主题都能回溯到代表样本和原句
3. 前端既能看长期沉淀，也能看月度新增
4. token 成本可控，大模型只用于当月主题归纳

## 最终定义

本方案不是重做一套新的邀约质检系统，而是在现有邀约单条优劣势打标能力之上，增加一层面向培训沉淀的月度主题化组织能力。

职责划分如下：

- 单条质检层：继续负责每条邀约通话的优劣势打标
- 月度训练层：从成功样本中筛选优秀动作并归纳培训主题
- 话术库展示层：把主题、推荐话术和代表样本组织成长期可复用的优秀话术库
